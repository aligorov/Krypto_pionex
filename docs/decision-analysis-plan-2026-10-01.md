# Модуль «Анализ решений» — полный план (v1)

Дата: 2026-10-01. Статус: спецификация закрыта (4 итерации проектирования), ждёт «делай».
Замена отключённого свечного бэктест-гейта: доказательства из собственных живых решений системы.

---

## 1. Цель

Система сегодня не имеет памяти на собственных решениях: каждый спор о гейте/пороге решается релизом на живые деньги. Модуль делает решения наблюдаемыми и переигрываемыми:

1. **Объяснить** конкретный отказ («бот правильно отказался или упустил возможность?»).
2. **Проверить** изменение порога на записанной ленте до изменения боевых настроек.
3. **Оценить** вклад гейтов в $ по завершённым виртуальным исходам, с режимной группировкой и силой доказательства.

## 2. Архитектурные инварианты (несмещаемые)

1. Модуль — **наблюдатель, не участник**: единственные точки контакта с торговым путём — снимок решения в момент вердикта и подписка на существующие события (`bot_execution_events`, lifecycle, `reconciliationState`). Ноль новых ветвлений в deploy-цепочке.
2. Ошибка аналитики = **потерянное наблюдение** (видна в coverage), торговый путь живёт по своей политике. Запись best-effort: ограниченное время, без бесконечных ретраев, счётчик потерь.
3. **ALLOW ≠ открытый бот**: допуск → отправка → подтверждение биржи → валидный `buOrderId` → RUNNING (правило 4 AGENTS.md). Модуль читает существующую лестницу, не строит вторую; таймаутная неопределённость и её разрешение фиксируются.
4. **Исторический кандидат автоматически не открывается.** Replay/shadow не создают ботов, не шлют заявки в Pionex, не занимают слоты/капитал. Изменение политики = правка настроек оператором в PostgreSQL.
5. Kill switch, маржа, risk-engine обязательны всегда; override живёт только внутри run_id эксперимента.
6. Shadow-символы не попадают в WS-prewarm и API-бюджет — цены только из уже собираемых тикеров/свечей (урок v2.0.164).
7. **Все агрегаты GROUP BY режим среза** (RANGE/TREND_UP/TREND_DOWN, ADX/Hurst-класс). Никаких «за всё время» без режима — лонговая неделя не отвечает за шорты.
8. Автоматическое изменение боевых порогов **запрещено в v1**. Shadow предлагает цифры, решение за оператором.

## 3. Сценарии по вердикту

| Вердикт AutoGrid | Действие модуля |
|---|---|
| REJECT | Запись гейта, входов, порога, исключения, доступной геометрии (со стадией). При подходящих данных — виртуальное наблюдение (shadow) |
| WAIT | Запись причины (инфраструктурный WAIT ≠ рыночный отказ; в контрфакт не попадает, только в coverage) + связка с последующей попыткой через episode_id |
| ALLOW | Сохранение параметров допуска + отслеживание фактического создания (лестница buOrderId) |

## 4. Модель данных (миграция 0062, поверх существующих таблиц)

### 4.1 `entry_decisions` (расширение, миграция 0052)
Одна строка = одна попытка (трасса гейтов одним jsonb, не по строке на гейт):
- `episode_id`, `attempt_no` — связка попыток (символ+направление+политика объединения);
- `observed_at / available_at / decision_at` — паспорт времени каждого показателя;
- `data_quality` — OK/MISSING/STALE/DESYNC/ERROR (RV=0 при ошибке свечей ≠ отсутствие волатильности);
- `gate_trace` jsonb: `[{gate, verdict: PASS/REJECT/WAIT/EXEMPT/NOT_EVALUATED/UNKNOWN, threshold, exemption, inputs{...}}]` — из уже выполненных проверок, без дозапросов к бирже после отказа;
- `stage` — SCANNER/INTERMEDIATE/FINAL (геометрия на раннем отказе = неизвестна, не досчитывать симуляцией);
- `config_snapshot` jsonb — значения настроек и feature-флагов (хеш не восстанавливает значения) + версии кода/цепочки;
- `direction_before_override / direction_after_override`;
- цена и её источник на момент решения.

### 4.2 `shadow_candidates` (расширение, миграция 0031)
- привязка `episode_id` + `decision_id`;
- стадия геометрии; TP/SL/инвестиция/модель PnL фиксируются при создании наблюдения;
- причина отсутствия shadow при отказе: CAP_REACHED / DUPLICATE_EPISODE / INVALID_GEOMETRY (в знаменателе coverage);
- **две машины состояний**: позиция (OPEN/CLOSED_TP/CLOSED_SL/HORIZON_END/INVALIDATED) × расчёт (PENDING/RUNNING/DONE/RETRYABLE_ERROR/INSUFFICIENT_DATA). Завершение горизонта — отдельный исход, не TP и не стоп;
- идемпотентное закрытие (повторный проход не начисляет PnL/комиссии дважды); захват задания с lease и сроком владения (многоворкерность, восстановление после рестарта из БД);
- `directional_mtm_proxy` — отдельным полем, не «$ гейта».

### 4.3 `replay_runs` (новая)
`run_id, период, baseline, override, версии кода/данных/модели, статус, причина остановки, статистика N/K/M/L (проверено / вердикт изменился / полная цепочка доступна / исход доступен), NOT_REPLAYABLE-причины`. Результат нового replay не переписывает старый.

### 4.4 `gate_value_snapshots` (расширение)
Окна 24ч/7д по режимам; coverage; завершённые/незавершённые эпизоды; декомпозиция PnL.

### 4.5 Ретеншн и объём
~185 кандидатов × ~360 сканов/сут ≈ 67к попыток/сут. Сырые трассы — 14 дней, эпизоды — 90 дней, агрегаты — бессрочно. Тяжёлые вычисления — пакетами через существующий worker.

## 5. Контракт ценовой траектории (для каждого исхода)

- начало/конец доступной истории, число наблюдений, самый длинный пробел, источник цены (mark/last/свечи);
- незакрытые свечи и неоднозначные события; правило исполнения при гэпе;
- **TP и SL в одной свече** → консервативный исход + альтернативный сценарий, показывать диапазоном;
- пропуск цен ≠ нулевой PnL и ≠ успешное завершение (→ INSUFFICIENT_DATA);
- онлайн-наблюдение по manage пропускает движения между проходами — ограничение сохраняется вместе с результатом.

## 6. PnL: декомпозиция и честность

PnL_net = PnL_grid + PnL_inventory − Fees − Funding − Slippage, хранится по компонентам.
MTM-прокси помечен списком учитываемых компонентов; не смешивается с grid-replay в одной сумме.

**Атрибуция (три уровня, не складываются между собой):**
1. исходы кандидатов, отвергнутых конкретным гейтом;
2. изменение допуска всей цепочки (прохождение изменённого гейта ≠ допуск — учитывается сохранённая трасса последующих);
3. эффект на портфель (слоты/капитал/замещённые сделки) — вне v1.

ΔPnL_proxy = Σᵢ (aᵢ_new − aᵢ_base) × PnL̂ᵢ, где aᵢ — допуск всей проверяемой цепочки, PnL̂ᵢ — модельный исход при фиксированных кандидатах/модели/инвестиции.

Метрики: EV/winrate/PF — по завершённым; Sharpe/Sortino/MaxDD — только при корректной equity-серии; turnover/ликвидность — при модели исполнения. Валидный первый вывод: «данных недостаточно».

**Контрольная группа ALLOW:** выбранная группа допущенных кандидатов симулируется тем же движком; для реально созданных ботов — сверка модельного vs фактического исхода (одна геометрия/горизонт/инвестиция; учёт траншей, re-center, ручных вмешательств из bot_execution_events). Ошибка модели группируется по направлению/режиму → границы применимости отчёта.

## 7. Интерфейс (API + панель + Telegram)

**Экран 1 «Почему бот не открылся»** — в карточке кандидата «История решения»: трасса гейтов (значение vs порог, EXEMPT-бейджи, NOT_EVALUATED), стадия геометрии, судьба shadow-эпизода. API: `GET /api/autogrid/decisions?symbol&scan_id`, `GET /api/autogrid/decisions/{id}` (read-only).

**Экран 2 «Проверить изменение»** — вкладка «Replay гейтов» в лаборатории: форма (гейт/новый порог/период) → «Сравнить» → таблица (вердикт изменился / допуск цепочки / исход доступен / данных недостаточно) + модельный эффект, предотвращённые потери, упущенная прибыль, качество данных. Кнопка **«Валидация модели»**: нулевой override по последним N — вердикты обязаны воспроизводиться + сверка с фактическими исходами; без зелёной валидации результаты помечаются «модель не откалибрована». API: `POST /api/autogrid/replay/run` (задание в PG, worker пакетами с lease; override только внутри run; торговых операций нет).

**Экран 3 «Качество гейтов»** — сводка 24ч/7д по режимам: гейт → эпизоды → покрытие → модельные ±$ заблокированных → достоверность. ТГ-суточная сводка со ссылкой.

## 9. Тесты (минимальный набор доверия)

| Проверка | Требуемый результат |
|---|---|
| Replay без override | Воспроизводит исходный вердикт или объясняет нехватку данных |
| Повторный запуск | Без дублей и повторных начислений |
| Стоп LONG/SHORT/NEUTRAL | Убыток по модели цены исполнения |
| Нет исторических цен | INSUFFICIENT_DATA, PnL неизвестен |
| Рестарт во время обработки | Задание восстанавливается (lease) |
| Смена настроек сегодня | Не меняет исторический эксперимент (снимок) |
| Ошибка телеметрии | Торговое решение сохраняется, потеря наблюдения видна в coverage |
| TP+SL в одной свече | Диапазон: консервативный + альтернативный |
| Кап shadow | Причина пропуска в знаменателе coverage |

Интеграционные — на disposable-postgres (pgx-правила: непрерывные $N, ::numeric, не глотать Exec).

## 10. Условия отклонения вывода об «улучшении»

Неполные снимки; несопоставимые модели PnL; систематические пропуски из-за капа; неизвестные последующие гейты; смена знака после комиссий/funding/slippage; перебор порогов на одной истории (Bailey/PBO — защита §15 отдельным этапом). Рыночные: гэпы, ликвидность, смена режима, коррелированные позиции.

## 11. Вне v1 (осознанно)

Автоприменение порогов; портфельный replay с замещением сделок; пограничные когорты; карта взаимодействий гейтов; сценарии исполнения (ухудшенные комиссии/задержка); новый PnL-движок взамен существующего 5M-replay.

## 12. Ожидания

Первые достоверные контрфакт-агрегаты — после накопления завершённых траекторий (цикл созревания 24ч, пакеты раз в ~20ч); значимая режимная статистика — 5-7 дней ротации. Первый полезный вывод может быть «данных недостаточно» — это нормальный результат, а не сбой.
